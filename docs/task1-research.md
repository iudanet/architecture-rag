## 3. Сравнение эмбеддингов

Итоговые цифры по индексации одной и той же базы (37 документов, 419 чанков),
`progress.md`, раздел «Сравнение эмбеддеров — ИТОГ»:

| | USER-bge-m3 локально | Яндекс text-embeddings |
|---|---|---|
| Индексация 419 чанков | 2094.7 с (35 мин) | 158.1 с (2.6 мин) |
| Среднее время запроса | 0.56 с | 0.42 с |
| Размерность | 1024 | 1536 |
| Батчи | до 32 | не поддерживает |
| Score на 5 контрольных вопросах | 0.522–0.609 | 0.574–0.656 (везде выше) |
| Приватность | данные в контуре | уходят в облако |

Облачный эмбеддер быстрее локального **в ~13 раз** и даёт выше score на всех
контрольных вопросах. На вопросе про капитана локальный вторым результатом
выдал другого персонажа, Яндекс оба раза попал в нужный документ.

Особенности API Яндекса, найденные экспериментально:

- батчи не поддерживаются: пачка из 2+ текстов → HTTP 400 `Array input must contain
  exactly one string`, запросы идут по одному;
- библиотека `openai` по умолчанию шлёт `encoding_format=base64`, Яндекс отвечает HTTP 400
  `Base64 encoding format is not supported` — воспроизведено на всех трёх семействах моделей
  каталога, исправлено явным `encoding_format="float"` в `rag/core.py`.

Отклонённые варианты локального инференса:

| Вариант | Причина отказа |
|---|---|
| TEI (`text-embeddings-inference:cpu-1.8`, 686 МБ) | без ONNX-весов падает на Candle, прогрев BGE-M3 > 5 мин, API не открывается |
| `embeddinggemma:300m` через Ollama | 0.5 эмб/сек, нет батчинга — индексация заняла бы 21 мин на корпусе меньшего объёма, непригодно |

Итог: облако выигрывает по скорости и качеству, локальный инференс — только по
приватности, а для QuantumForge это решающее требование.

## 4. Сравнение векторных БД

| | Qdrant | FAISS | ChromaDB |
|---|---|---|---|
| Скорость поиска | HNSW, сравнима с FAISS на 419 точках (0.4–0.6 с с учётом сети до эмбеддера) | быстрее всех (in-process, без сети) | сопоставима с Qdrant на малых коллекциях |
| Скорость индексации | зависит от эмбеддера, не от БД | зависит от эмбеддера, не от БД | зависит от эмбеддера, не от БД |
| Сложность внедрения | 1 контейнер, HTTP+gRPC API из коробки | библиотека, персистентность и сервер нужно писать самому | embedded или клиент-сервер, проще FAISS, беднее по фильтрации |
| Payload-фильтрация по метаданным | есть из коробки (`FieldCondition`, `MatchValue`, `Range`) | нет — своя реализация поверх индекса | есть, но менее выразительная |
| Снапшоты / бэкап | встроены (`/collections/.../snapshots`) | нет, вручную сериализовать индекс | есть, проще |
| Стоимость владения | 1 контейнер, том для данных | своя обвязка (сервер, персистентность, фильтры) — дороже в разработке | 1 контейнер/библиотека, дешевле Qdrant в эксплуатации, беднее возможностями |

Выбор — **Qdrant**: слой защиты (Задание 5) отбрасывает чанки с меткой
`suspicious=true` до генерации ответа, для чего нужна payload-фильтрация по
метаданным на уровне БД, а не постфильтрация в приложении. Qdrant даёт это
из коробки (`FieldCondition`/`MatchValue`), плюс снапшоты и HTTP+gRPC доступ.
FAISS потребовал бы отдельно писать персистентность и фильтрацию — вне объёма
учебного проекта.

## 5. Конфигурация сервера

Замер контейнера эмбеддингов (Infinity, `USER-bge-m3`, батч 32) в процессе индексации:
**404% CPU, 1.5 GiB RAM**. Образ Infinity CPU — 2.34 ГБ, вес модели — 1.1 ГБ.

Вывод: инференс эмбеддингов упирается в CPU, а не в память — RAM почти не
расходуется сверх веса модели. Рекомендация по железу отталкивается от числа
ядер CPU (или наличия GPU), а не от объёма RAM:

| Ресурс | Минимум | Комментарий |
|---|---|---|
| CPU | 8 ядер | контейнер эмбеддингов утилизирует 4+ ядра параллельно (замер 404%) |
| RAM | 4 ГБ | 1.5 GiB занято при индексации + запас под ОС и Qdrant |
| GPU | не обязателен, но кардинально ускоряет | при наличии GPU индексация быстрее CPU-варианта на порядок, замера на GPU в проекте не производилось |
| Диск | 4 ГБ | образ Infinity 2.34 ГБ + вес модели 1.1 ГБ + индекс Qdrant |

## 6. Варианты конфигурации

| Вариант | Стоимость | Приватность | Качество | Сложность |
|---|---|---|---|---|
| Полностью локальный (Ollama LLM + Infinity embeddings) | железо, без оплаты за токены | документы и запросы не покидают контур | ниже облачного по CoT и скорости | выше — своя инфраструктура GPU/CPU |
| **Гибрид: локальные эмбеддинги + облачная LLM (выбран)** | оплата токенов LLM + железо под эмбеддинги | документы не покидают контур на этапе индексации/поиска, в LLM уходит только текст вопроса и найденных фрагментов | CoT и следование инструкциям — на уровне облачной модели | средняя — 1 локальный контейнер + облачный API |
| Полностью облачный (эмбеддинги + LLM в облаке) | оплата токенов и запросов эмбеддера | документы уходят в облако целиком | лучшее — Яндекс выигрывает и по эмбеддингам, и по LLM | минимальная — только `.env` |
| Облачный на YandexGPT (LLM Яндекс, эмбеддинги локальные) | оплата токенов LLM Яндекс + железо под эмбеддинги | как у гибрида | как у гибрида, конкретно под YandexGPT | средняя |

Выбранная конфигурация — гибрид: локальные эмбеддинги (Infinity + USER-bge-m3) и
облачная LLM (YandexGPT 5.1).

## 7. Вывод

Итоговая конфигурация: локальные эмбеддинги (Infinity + USER-bge-m3, приватность),
облачная LLM YandexGPT 5.1 (скорость и качество CoT), векторная БД Qdrant
(payload-фильтрация для слоя защиты из Задания 5).
